# 05 · 架构设计

## 总览：全 Agent + 工具调用

珞珈智行的主链路是一个 **Plan-Act-Observe Agent 循环**：大模型负责理解需求、选择工具、传入空间参数；所有确定性计算（地点解析、路径规划、天气、路况）由工具层完成，大模型不接触图结构与坐标运算。

```
用户一句话（文字 / 语音转写 / 地图点选）
  │  POST /api/chat
  ▼
api/routes.py ──────────────────────────────────────────────
  │  注入 GPS 坐标 / 出行方式 / 地图途经点 / whu_uid / 上下文
  ▼
agents/planner.py · run_agent()  Plan-Act-Observe 循环
  │  system 上下文拼装：
  │    1) agent_system.txt        角色与铁律
  │    2) knowledge.py            静态校园经验任务卡（按 query 召回 ≤2 张）
  │    3) profile.py              该用户 EMA 画像权重（≥3 次采纳才注入）
  │    4) 本次状态                出行方式 / GPS / 途经点 / 多轮历史
  │
  │  LLM 决策（temperature=0，最多 6 轮 / 40s）
  │    ├─ 需要工具 → function calling → agents/tools.py 执行 → 结果回注 → 继续
  │    └─ 无需工具 → 自然语言最终答复
  ▼
agents/tools.py · 工具注册表（只做决策，不做计算 → 只做计算，不做决策）
  │  resolve_poi / get_place_details / search_poi_candidates / find_reachable_places
  │  plan_route / plan_via_route / plan_itinerary / plan_tour / plan_multimodal_route
  │  compare_routes / get_weather / list_road_conditions
  │  ask_user / suggest_followup
  ▼
spatial/ 空间计算层（NetworkX 图算法，无 LLM）
  │  routing.py  模式过滤 → 硬约束 → 路况/天气成本 → 加权 Dijkstra
  │  network.py  OSM 路网加载、标注合并、节点吸附
  │  poi.py      POI 数据、别名/数字归一、类别检索、顺路排序
  │  road_conditions.py / weather.py / coord_transform.py
  ▼
路径包（GCJ-02）+ 自然语言 → 前端 Leaflet 渲染 / 语音导航
```

**停电保险**：Agent 循环只在 LLM API 层面故障（断网、鉴权、限流，抛 `PlannerError`）时，由 `api/routes.py` 落回旧的 parser 单管道（`parser.py → routing.py → explainer.py`）。正常请求全程走 Agent，旧管道不是并行通道。

## Agent 循环（agents/planner.py）

- **预算护栏**：`MAX_TURNS = 6`、`TIME_BUDGET_S = 40.0`（gunicorn `--timeout 60` 内留余量）；单次 LLM read timeout 25s，失败 1 次重试。
- **工具错误自修正**：工具返回 `{"error": ..., "message": ...}` 时不中断循环，作为 tool 消息回注，LLM 可修正参数重试。
- **提前终止**：`ask_user` 调用即终止（等用户下一轮）；路径工具一旦产出路线立即收尾，不再让模型多跑一轮——避免 DeepSeek 在含 tool_call 的历史后把内部 DSML 标记当纯文本吐出；`_sanitize_message()` 也会剥离任何泄漏的 DSML 片段。
- **坐标不进模型决策**：路线坐标对 LLM 无意义且占 token，回注结果时压缩为"[N 个坐标点]"；完整坐标由 planner 从工具 artifact 取出直接进 API 响应（`tools.result_to_json()`）。
- **产物类型**：`response_kind ∈ route | candidates | clarify | chat`，路由层 `_agent_response_to_legacy()` 翻译成前端兼容的 task_type 结构。

## 工具层（agents/tools.py）

| 工具 | 作用 | 何时调（由 LLM 决策） |
|---|---|---|
| `resolve_poi` | 名称→校内 POI 确认（别名/模糊/同分歧义候选） | 地名不确定、需确认是否存在 |
| `search_poi_candidates` | 按 subcategory/类型/关键词/季节检索，可限定 near_poi 带距离 | "想吃饭/喝咖啡/跑步"只有目的没有点 |
| `plan_route` | A→B 多因素路径 | 起终点都明确 |
| `plan_via_route` | 带途经点路径；via 支持点名、给类别（自动顺路排序取最顺）、给坐标 | "上课路上顺便买个笔记本" |
| `plan_tour` | 多点游览，自动选点排序、环线/开放线 | "逛遍全校""推荐赏樱路线" |
| `get_weather` | 武汉实时天气 + 出行影响（湿滑/高温/低能见度） | 问天气/带伞/能否出门，禁止凭印象答 |
| `list_road_conditions` | 当前生效的封路/施工/积水/事故/活动 | 问管制、Agent 判断可能影响路线时 |
| `ask_user` | 反问澄清（终结本轮） | 缺起点、地名多候选 |
| `suggest_followup` | 2~3 个跟进问法芯片 | 最终答复前 |

工具 schema 集中在 `TOOL_SCHEMAS`。偏好参数结构：

- `constraints`（硬约束）：仅在用户明确说"避开/不要"时设置，`slope=avoid` 等；
- `weights`（软权重）：distance/slope/scenery 各 ∈ [0.05, 0.90] 且和为 1；无偏好时**不填**，由后端按出行方式取默认值；
- `mode`：walk/bike/drive，默认 walk。

## 空间参数：约束与权重分离（DEC-011，仍有效）

- **硬约束**回答"能不能走"：如 `slope=avoid` 时剔除 `slope_level=5` 的边、level=4 施加 2× 距离惩罚；无可行路径时自动放宽保可达。
- **软权重**回答"更喜欢哪条"：在可行子图上做加权 Dijkstra。

成本函数（三指标方向统一为越小越好）：

```
Cost = w_d × D + w_s × S + w_v × (1 − V)
```

按出行方式的默认权重（`spatial/routing.py: MODE_DEFAULT_WEIGHTS`）：

| 模式 | distance | slope | scenery |
|---|---|---|---|
| walk（默认） | 0.90 | 0.05 | 0.05 |
| bike | 0.90 | 0.05 | 0.05 |
| drive | 0.90 | 0.05 | 0.05 |

普通"A 到 B"请求默认接近最短路线，避免无意义绕路；权重只在用户表达偏好时由 Agent 给出（prompt 中给了赶时间/避坡/看景三档示例）。路径长度上限 `min(最短路径 × 3, 2000m)`。

## 两层记忆

### 静态记忆 · agents/knowledge.py + data/task_cards.json

开发者沉淀的校园场景经验卡（9 张，如"赏樱""雨天""新生报到"）。每轮按触发词命中数召回 ≤2 张，当季卡片加权，作为 system 消息注入；卡片可携带该场景的参考权重。卡片少（<50），纯关键词匹配，不上向量检索。

### 动态记忆 · agents/profile.py + data/user_profiles.json

按前端生成的 `whu_uid` 持久化个体偏好，从用户**实际采纳**的路线权重中用 EMA 缓慢学习：

```
prior ← (1−0.3) × prior + 0.3 × 本次采纳权重
```

- 路线曝光、停留 20 秒和单纯点选均不学习；只有用户明确选择非最短休闲策略并开始或完成导航才更新权重；
- 同一 `route_id` 的开始与到达只记一个样本，避免重复强化；
- 至少 3 次采纳才把画像注入 prompt（先验不可靠宁缺毋滥）；
- 用户本次显式要求优先于画像；
- JSON 文件 + 线程锁，多 worker 偶发丢更新可容忍（软先验；规模化再换 SQLite/Redis）。

## 空间计算层（spatial/）

### 出行方式过滤

`filter_graph_for_mode(G, mode)` 返回模式子图。骑行/驾车剔除台阶、电梯、扶梯及步行专用边（一票否决）；步行使用 walk 全量路网（DEC-012：OSM 校园 footway 标注仅约 70%，不做 highway 二次筛选，否则路网碎片化）。台阶在步行成本中加 2.5×，食堂区域 10 条有向边人工标注 10× 软惩罚防穿楼（data/edge_overrides.json，覆盖数量以该文件为准）。

### 路况（全出行方式生效）

`CONDITION_EFFECTS`（spatial/road_conditions.py），`block` 为硬封禁、数字为成本倍数：

| 类型 | walk | bike | drive |
|---|---|---|---|
| closure 道路封闭 | block | block | block |
| construction 施工 | 1.5× | block | block |
| flooding 积水 | block | block | 1.5× |
| accident 事故 | 1.3× | 1.3× | block |
| event 活动管制 | 1.2× | 1.2× | block |

事件绑定具体路段：管理员点击点服务端重新吸附（不信任前端坐标），再沿拓扑向两端延伸成"路口到路口"的边链。支持 start_time/end_time 定时生效。硬封禁导致不可达时降级为超大惩罚保路线可用。

### 天气成本

高德实时天气快照（weather.py）注入路径计算：湿滑/高温/低能见度转成相应成本或提示；天气接口失败静默跳过，不阻断规划。

### 途经点与游览

- `compute_via_route`：A→via→B 两段分别计算；类别型途经点先用"绕行比"排序（`rank_via_candidates`，阈值 1.5），取最顺路者；
- `compute_tour`：按主题选点（赏樱/湖畔/地标/全校风景），多点排序生成环线或开放线，总长上限 6000m，不可连通的点丢弃。

模型主导的多点出行中，游览地点与用户出发点分别保存。缺少用户给定或地图选定的出发点时，先询问出发位置，并保留已提出的游览地点供后续续接。已保存游览地点的行程在交付前核对路线是否包含这些地点。用户明确只查看地点之间的独立参考路线时，可以不提供自己的出发点，结果会注明未包含从用户出发的路段。

### 转向指令

`build_turn_by_turn(G, nodes, mode)` 生成路口级逐步指令（depart/直行/转弯/arrive/via），动作点随路径转 GCJ-02 下发，供前端实时导航与语音播报。

## 坐标系统（关键约束）

| 数据 | 坐标系 |
|---|---|
| 前端地图（Leaflet 高德瓦片）、POI、GPS 展示、路况点击 | **GCJ-02** |
| OSM 路网、路径图计算、DEM 坡度 | WGS-84 |

边界转换集中在 `spatial/coord_transform.py`：API 入参 `gcj02_to_wgs84()`，出参（路径、转向点、沿途 POI）`wgs84_to_gcj02()`。前端只允许接 GCJ-02 瓦片（高德矢量 style=8 / 卫星 webst style=6+8），接 OSM/Esri 等 WGS-84 源会产生约 50–500m 偏移。

## 关键设计原则

1. **LLM 只做两件事**：把人话变成工具调用（含空间参数）、把结果说成人话。计算与事实一律来自工具。
2. **能确定的不交给概率**：坐标转换、地点归一、关键词出行方式纠偏、槽位承接、权重边界裁剪都在确定性代码里。
3. **每一处 LLM 都有兜底**：API 故障落旧管道，工具失败回注自修正，解释失败用模板，天气失败静默跳过。
4. **研究链路可度量**：weights 由 LLM 直出（DEC-010），applied_weights 随响应下发并经 telemetry 回流，`experiments/` 保留规则/固定权重/最短路径基线做对照。
