# 积水图片免圈选原型与误报记录

日期：2026-11-11。

## 当前状态

本记录对应隔离工作区 `codex/flood-auto-review-20261111`，基于 `e999892` 开发。**免圈选实现尚未发布，也没有替代现行人工圈选流程。** 事故模型未开启。原有桌面工作区中的未提交资料没有改动。

原型允许对单张图片自动提取 Doodleverse v7 的“淹水道路”类别连通区域，最多展示 24 个候选；超出上限时提示结果不完整。每个候选单独核对，可查看对应的图像轮廓；真实路况仍需要人工确认、选择道路边以及完成既有绑定校验。公开素材的试用结果不能发布为真实道路事件。模型推理失败与没有检出候选分开处理。

新流程采用全图类别最大值和连通区域，不再是原来限定在人工圈选路面内、按区域积水比例触发的规则；因此旧版数值与资源验收**不能直接视为新流程的发布验收**。原型中的常规 worker 不对外声明自动能力，遇到未获验收的自动任务也会拒绝处理；只有隔离测试显式注入能力以检查工程链路。已有生产清单的批准范围不应被默认为自动候选流程已获批准。

## 公开影像上的实际问题

对用户展示图片 `HURRICANE-IAN_000491`，自动流程提取 24 个候选并触及上限。将所展示的候选轮廓并集与该公开数据的道路标注比较，轮廓像素约 88.25% 落在道路标注之外；轮廓覆盖了约 65.63% 的已标注淹水道路像素。另一张无淹水道路标注的公开图片 `HURRICANE-IAN_000774` 仍生成 23 个候选，候选轮廓均在道路标注之外。

这些数字是已使用过的单图诊断，不是独立测试或校园现场精度。轮廓是图像中的疑似区域，不是经过地理配准的路段或实际通行状态。标注只用于预测之后的对照，没有输入模型。完整逐图结果、影像及标注哈希保存在：

`D:\LuoJiaValidation\flood_auto_review_20261111\public_examples_automatic_diagnostic.json`

使用先前保存的 64 张公开验证图片概率图做全图阈值诊断，单纯调整类别概率阈值未能消除大量非道路响应；该诊断并非当前连通区域算法的完整评估，不能拿它冒充现场精度。结果见 `validation_full_image_threshold_diagnostic.json`。

随后使用同一组 64 张图和实际 ONNX 模型重新运行当前自动轮廓提取：轮廓并集中约 93.08% 的像素不在道路标注内；按像素汇总，约 5.10% 的轮廓像素落在标注的淹水道路上，约 6.29% 的已标注淹水道路像素被轮廓覆盖。30 张道路未标注积水的图中，27 张生成了至少一个候选。候选数量不限于重大区域，因此这一干燥图结果表示“有候选”，不是事件级误报率。详情、逐图数据与哈希见 `automatic_proposals_validation_diagnostic.json`；这些先前已用过的公开样本不能替代独立测试或校园现场测试。

试查的三个额外公开道路分割权重均不能直接解决此问题：`imastikbaev/deepglobe-road-segmentation`、`teohyc/Satellite-Road-Segmentation-UNet` 和 `CurviWeave` 在所查的公开洪水样例上均明显漏掉被淹道路，不能作为已通过的生产方案。CurviWeave 的本机 CPU 对照及模型哈希见 `curviweave_public_sample_diagnostic.json`；Windows 进程内存读数不等于 Linux 资源限额验收。上述模型均未接入产品。

另检查了公开的 DC4Former FloodNet 权重，但代码仓库未见明确许可。为避开本机缺失的 MMCV 原生扩展，隔离环境按公开配置临时重建推理头并对权重作严格匹配；这一适配尚未与作者原始推理程序对齐。探索性结果显示：在 `000491` 图上，约 8.36% 的已标注淹水道路像素被识别；在另外两张有淹水道路标注的图片上未检出该类别。因此不能将这一临时适配当作可靠方案，更不能将数字归为官方原实现的正式测试成绩。详情及权重哈希见 `dc4former_public_sample_diagnostic.json`。

探索过“用同地点灾前参考影像识别道路，再叠加灾后积水概率”的方法：在用户展示图上，疑似积水像素中属于标注淹水道路的比例从约 8.93% 提高到约 66.12%，但覆盖的标注淹水道路仍只有约 50.77%。将此方法应用于 64 张同来源验证图，30 张有淹水道路事件的图中检出 5 张，30 张干燥道路图中正确排除 23 张，且 7 张图无法识别出道路；这仍不可用。复查记录见 `predisaster_reference_sample_diagnostic.json` 和 `paired_validation_diagnostic.json`。该方法需要准确对齐的前后影像；当前用户上传的展示 PNG 没有位置或相机元数据，不能据此自动找到对应的灾前图。所用额外道路权重的使用权限也尚未核定，不作为产品依赖。

还取得 [SpaceNet 8 获奖方案](https://github.com/SpaceNetChallenge/SpaceNet8) 作者公开的双时相 `best_flood.pt`，SHA-256 为 `c7f5ac3fe6da2e3d7536fc432aa8cb7efa6eb9f6f1e183eea091f901afc8df29`。使用其模型结构、通道归一化和 0.9 洪水类别阈值，在四张已用过的 512 像素公开图对上做本机 CPU 探索：展示图在 16,879 个标注淹水道路像素中只识别出 4 个；另外两张正例分别识别出 0 和 102 个。未加 0.9 阈值时展示图仍仅覆盖约 4.55%。运行进程在 Windows 上模型加载后的驻留内存约 711 MiB，四图期间峰值工作集约 1,321 MiB；这些数字不等于 Linux 生产 cgroup 验收，也不能证明转换后所需的资源。原模型为 1300 像素场景设计，512 像素、不同来源和场景的这次结果存在域差异，不能当作该模型在原数据上的性能。完整结果保存在 `spacenet8_public_pair_diagnostic_streamed.json`，权重使用条件仍需核实；未接入产品。

- 使用真实 Service Worker，以生产基线 `e999892` 的网页缓存升级到候选缓存再回退：1 项通过。
- 按现有人工圈选清单走正式 worker 启动路径，试用与校园图片任务使用真实权重完成处理：1 项通过；自动能力在心跳中明确为关闭。该检查不构成自动模式的验收。

正常 worker 启动检查最初发现状态信息超过 500 字符时会被截断，导致能力 JSON 解析失败。原型中已移除该文本截断，并添加长能力记录经数据库写入和接口读取的回归检查；数据库字段本身为 `TEXT`，不需要迁移。失败记录未覆盖。
