## 结论

离线筛查了 [SmolVLM-256M-Instruct](https://huggingface.co/HuggingFaceTB/SmolVLM-256M-Instruct)，希望它作为图像级辅助判断，帮助排除干燥道路。固定问题和 512 像素预处理后，16 张已使用过的 Delta 图全部回答“有积水道路”，其中 8 张未标注淹水道路；其“有 / 无”首词分数差在这组图上的配对排序 AUC 为 0.375。样本量小，分数不是经校准的概率；这一检查不足以证明模型在其他场景中的表现，但足以说明**该配置不能作为当前免圈选候选的可靠过滤器**。

模型只输出图像级文字，本身不提供道路轮廓；即便图像级结果通过，也仍需可靠的道路定位、逐项人工复核及独立验收。此次没有将模型接入产品，没有训练模型、使用付费计算或变更生产，自动候选继续关闭。

- 所有推理只在本机使用 CPU、FP32 和两个线程，生成过程关闭随机采样；图片没有发送给外部服务。红色、蓝色合成图片的输入张量哈希不同，模型分别回答红色和蓝色，说明本次调用的视觉输入能够影响输出；这不能证明洪水判断可靠。

- 默认 17 图块的 Windows 进程峰值工作集约 3,682—3,746 MiB；单图块 FP32 筛查约 1,874—1,906 MiB。以上不是 Linux cgroup 资源验收，也不能据此判断量化或其他部署实现一定不符合 640 MiB。

## Transformers 版本差异

同一展示图、同一提问和同一模型权重，默认预处理下 Transformers 4.57.0 回答“Yes”，5.13.0 回答“No”。两个版本的文本 token 和注意力掩码数值一致，图像张量形状一致但像素数值有细微差异；为排除预处理影响，将 **4.57.0 序列化的同一份输入张量**分别送入两版模型，首词仍分别为“Yes”和“No”。

代码对照发现，两版 `Idefics3VisionEmbeddings.forward` 使用不同的图像块位置编号：4.57.0 在坐标计算后乘以 `1 - 1e-6`，5.13.0 使用上限裁剪。对 512×512、16 像素图块的完整方形输入，两种方法在每个方向的 32 个位置中有 31 个编号不同。

仅在隔离的 5.13.0 进程中临时使用 4.57.0 的该函数，并再次输入完全相同的张量，生成首词变为“Yes”，全部首词分数与 4.57.0 的对应数组逐项完全一致。该反事实验证定位了**这一次运行**中的差异来源；它不证明哪个版本对所有输入更准确，也不改变任何已安装包或产品代码。

5.13.0 加载时还打印了一条关于默认 `pad_token_id` 的警告。检查模型实际生效配置和 tokenizer 后，文本词表为 49,280、文本 pad ID 为 2、图像 token ID 为 49,190，均在有效词表范围内。上述位置函数对照已复现该样本的输出差异；没有据此推断警告对其他输入一定无影响。
