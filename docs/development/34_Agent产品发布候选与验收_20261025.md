# Agent 产品发布候选与验收（2026-10-25）

## 范围与决定

从 `main` 提取用户可感知的修复，形成 `codex/agent-release-candidate`。研究分支的模型用量探针、固定天气注入、实验脚本、已见题和运行证据不进入本候选。桌面主工作区的未提交材料未被修改。

候选包含：明确地点缺起点时保留目的地并追问起点；只有明确起点时追问目的地并保留策略；多阶段活动在选择候选后继续后续地点；防止“刚才的起点”被当作新地点；复合天气与路况请求反馈实际取得的信息；开放式活动途经点不被误识别为具名地点；多段路线的文字总览按顺序点名途经点；三处集贸市场 POI 的学部字段修正。修改集中在 `agents/planner.py`、`agents/task_planner.py`、`agents/tools.py`、`api/routes.py`、`spatial/poi_taxonomy.py`、`data/pois.json`，并附对应回归测试。

补充验收：实际模型请求“从武汉大学信息学部出发，先找附近能打篮球的地方，再到星湖园食堂”返回两段图内通过路线，终点依次为信息学部篮球场、星湖园食堂。首次探针暴露两个问题：文字总览遗漏途经篮球场，且在未要求“最近”时自动代选了球场。新增回归先复现失败，修复后此请求先展示 3 个篮球场候选；选择其中一个后，返回依次经过该球场和星湖园食堂的完整路线，文字总览也列出球场。相关 151 项测试通过，第二轮端到端本地数据探针通过；这仍不代替生产前端与 Android 验收。

合并前代码审查进一步发现三阶段活动被具名终点覆盖、后续路段丢失路线策略、具名途经路线漏答路况，以及修复过程中自定义权重状态校验、硬约束误改策略和“少走坡”误判等回归风险。已对这些场景逐项编写先失败后通过的回归用例；多轮地点需求增加可持久化的受支持策略字段，后续路段沿用已选策略，本轮显式修改优先；路况反馈同时检查原任务和本轮选择。最终全仓复跑见上表。

## 合并与线上核对

候选提交 `60d8ee6e1e834fc966ea76a4e7d3eca3f4ac2fbf` 已快进到 GitHub 与 Gitee 的 `main`，腾讯云服务器也更新到该提交。`whu-walker`、`whu-agent-worker`、`whu-vision-worker` 均为 `active`；用户页和管理页返回 HTTP 200，`/health` 返回 `ok`。生产 `data/pois.json` 的 Git blob 为 `65a40752aadf5eea545fb6ed4ff74d152e52b015`，与本地提交一致；Windows 与 Linux 工作区的文件字节哈希因换行符不同，不能据此判断数据内容不同。服务器原有的三个未跟踪文件保持原样。

线上真实请求“从玉兰2门经卓尔体育馆到星湖园食堂，当前有无道路管制？”返回 `route_kind=via`，起终点正确，约 1708.5 m、13 个步骤，图内核验 `pass`。答复为“本次未取得可核实的路况应用信息”，因此这项探针只证明多点路线和审慎反馈在线上可用，**不证明路况记录已覆盖这些道路**。
